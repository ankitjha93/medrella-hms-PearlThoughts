    USERS {

        varchar email "Unique login email"
        varchar phone "Contact phone"

        boolean is_used "Consumed flag"

    %% 3. DOCTOR MODULE

        uuid id PK "Primary Key"

        varchar first_name "First name"

        decimal rating_average "Average ratings"

    }

    DOCTOR_AVAILABILITY {

        int day_of_week "0=Sun to 6=Sat"
        time start_time "Start time"

    }

    TIME_SLOTS {
        uuid id PK "Primary Key"

        uuid availability_id FK "Parent rule"
        date slot_date "Calendar date"
        time start_time "Start time"

        varchar slot_type "REGULAR | ELASTIC"
        int max_capacity "Capacity limit"
        int current_bookings "Booked count"
        varchar status "AVAILABLE | BOOKED"

    }

        text reason "Chief complaint"

Schedule Project Module • Data Dictionary & Specifications

Third Normal Form (3NF) relational tables, foreign key constraints & design decisions

Database Specification

1. User & Patient Modules

Separation of Concerns: USERS handles authentication credentials, password hashing, and OAuth tokens. PATIENTS maintains clinical demographic data linked 1:1 via user_id to ensure compliance and zero redundant profile fields.

2. Doctor & Availability Modules

Elastic Scheduling: Doctors configure recurring shift rules via DOCTOR_AVAILABILITY, while TIME_SLOTS supports REGULAR and ELASTIC slot types with capacity limits to prevent double-booking while accommodating walk-ins.

Core Data Dictionary

Module Table Column Data Type Constraints & Keys Description
1. User users id, email, password_hash, role, auth_provider UUID, VARCHAR PK, UNIQUE(email), Role: DOCTOR|PATIENT|ADMIN Core authentication entity and role governance
verification_tokens id, user_id, token, expires_at, is_used UUID, VARCHAR, TIMESTAMPTZ PK, FK -> users(id) ON DELETE CASCADE Manages OTPs, verification links, and password resets
2. Patient patients id, user_id, first_name, last_name, dob, blood_group UUID, VARCHAR, DATE PK, FK -> users(id) UNIQUE (1:1), NOT NULL Patient demographics, emergency contacts, medical baseline
3. Doctor specializations id, name, description UUID, VARCHAR, TEXT PK, UNIQUE(name) Normalized medical specialties (Cardiology, etc.)
doctors id, user_id, specialization_id, license_no, fee UUID, VARCHAR, DECIMAL PK, FK -> users(id) (1:1), FK -> specializations Doctor professional profile, verified licenses, fees, ratings
4. Availability doctor_availability id, doctor_id, day_of_week, start_time, end_time UUID, SMALLINT, TIME PK, FK -> doctors(id) ON DELETE CASCADE Recurring weekly availability window definition
time_slots id, doctor_id, slot_date, start_time, max_capacity UUID, DATE, TIME, INT PK, FK -> doctors(id), slot_type: REGULAR|ELASTIC Concrete calendar booking slots with concurrent capacity control
5. Appointment appointments id, patient_id, doctor_id, slot_id, status, reason UUID, DATE, TIME, VARCHAR PK, FK -> patients, doctors, time_slots Core booking transaction and status lifecycle tracking
reschedule_history id, appointment_id, previous_slot_id, new_slot_id UUID, VARCHAR, TIMESTAMPTZ PK, FK -> appointments(id) ON DELETE CASCADE Complete audit trail for appointment timing changes and reasons
